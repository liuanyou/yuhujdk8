# Activity 079: Interface Call Stub Crashes on Non-Virtual Methods — itable_index = -2, x9 = NULL

## Date
2026-08-07

## Status
**Resolved** — root cause confirmed by inspecting `Method::_vtable_index` and `ciMethod::itable_index()`. Fix: check `itable_index() >= 0` before generating itable dispatch stub; fall back to direct call for non-virtual methods.

## Problem Description

A Spring Boot application crashes with x9 = 0x0000000000000000 during interface method dispatch in the Yuhu-compiled code. The crash occurs inside the itable dispatch stub generated by `YuhuRuntime::generate_interface_call_stub`, at the assembly sequence that loads the method from the itable:

```asm
add  x9, x11, w8, sxtw       // x9 = receiver_klass + itableOffsetEntry.offset
ldr  wzr, [x9, x10, lsl #3]  // x9 = [x9 + itable_index * 8]  ← x9 = NULL
```

The receiver klass is valid (e.g. 0x7c0019c98), but the loaded method pointer is NULL.

## Diagnostic Path

### Step 1: Verify itable dispatch computation

The itable dispatch code in `yuhuRuntime.cpp` lines 706-715 was compared against the reference implementation in `macroAssembler_aarch64.cpp` lines 928-1005. The computation structure is correct:

- `itableOffsetEntry::offset` is relative to the klass pointer (confirmed via `SetupItableClosure` at `klassVtable.cpp:1285-1305`)
- The search loop correctly scans `itableOffsetEntry` entries
- The final method load uses `klass + offset + itable_index * 8`, matching the reference

### Step 2: Check the itable_index value

Inspection of the `target_method` reveals `itable_index() = -2`. From `method.hpp:448-466`:

```cpp
enum VtableIndexFlag {
    itable_index_max        = -10, // first itable index, growing downward
    pending_itable_index    = -9,  // itable index will be assigned
    invalid_vtable_index    = -4,  // distinct from any valid vtable index
    garbage_vtable_index    = -3,  // not yet linked; no vtable layout yet
    nonvirtual_vtable_index = -2   // there is no need for vtable dispatch
};

bool has_itable_index() const  { return _vtable_index <= itable_index_max; } // <= -10
int  itable_index() const      { return itable_index_max - _vtable_index; }  // -10 - _vtable_index
```

The `_vtable_index` field encodes both vtable and itable indices:
- `>= 0` → valid vtable index
- `-2` → `nonvirtual_vtable_index` (no virtual dispatch needed)
- `<= -10` → has itable index (actual index = `-10 - _vtable_index`)

A `_vtable_index` of `-2` means the method is **non-virtual** and does **NOT participate in itable dispatch**.

### Step 3: Trace the call site generation

In `yuhuTopLevelBlock.cpp:1613-1616`, the `is_interface` branch unconditionally calls `get_interface_callee`, which generates an itable dispatch stub via `generate_interface_call_stub`. The stub uses `target_method->itable_index()` to compute the method offset.

`ciMethod::itable_index()` at `ciMethod.cpp:301-309` returns `Method::nonvirtual_vtable_index` (-2) when `!has_itable_index()`:

```cpp
int ciMethod::itable_index() {
    check_is_loaded();
    assert(holder()->is_loaded(), "must be linked");
    VM_ENTRY_MARK;
    Method* m = get_Method();
    if (!m->has_itable_index())
        return Method::nonvirtual_vtable_index;  // returns -2
    return m->itable_index();
}
```

The stub then computes: `x9 = x9 + (-2) * 8 = x9 - 16`, reading from **before** the itableMethodEntry array → hits zeroed memory → x9 = NULL.

## Root Cause

The `do_call()` method in `yuhuTopLevelBlock.cpp` does not check whether the interface method has a valid itable index before generating the itable dispatch stub. Methods with `_vtable_index == -2` (nonvirtual) — such as static interface methods or methods resolved to non-virtual targets — cannot be dispatched via itable.

## Fix

In `yuhuTopLevelBlock.cpp`, check `call_method->itable_index() >= 0` before using itable dispatch. If the method has no itable index, fall back to direct call:

```cpp
else {
    assert(is_interface, "should be");
    if (call_method->itable_index() >= 0) {
        callee = get_interface_callee(receiver, call_method, &compiled_entry_address, &stk_basic_types);
    } else {
        // Method has no itable index (e.g. static interface method or non-virtual).
        // Fall back to direct call instead of itable dispatch.
        callee = get_direct_callee(call_method, &compiled_entry_address, &stk_basic_types);
    }
}
```

`get_direct_callee` calls the method's `_from_compiled_entry` directly — no dispatch table needed. This is correct for non-virtual methods.

## Deferred Issue: Metadata GC Tracking in YuhuRuntimeStub

### The Problem

During investigation, a secondary issue was identified: `YuhuRuntimeStub` does not participate in the GC's metadata tracking for class unloading.

The `interface_klass` pointer embedded in the stub via `metadata_Relocation` is **not tracked** by the GC's class unloading machinery:

1. `nmethod::metadata_do(f)` iterates metadata references in nmethods (immediate values in instructions, virtual call CompiledIC holders, and the metadata section). Called by `MetadataOnStackMark` to set `_on_stack` flag on metadata, preventing deletion during class unloading.

2. `CodeCache::alive_nmethods_do(f)` only iterates **nmethods**, not RuntimeStubs.

3. `YuhuRuntimeStub` extends `RuntimeStub` → `CodeBlob`. It has no `metadata_do` override and no metadata section.

4. `Metadata::mark_on_stack` sets the `_on_stack` flag. During class unloading, `ClassLoaderData::free_deallocate_list()` at `classLoaderData.cpp:437` checks `if (!m->on_stack())` — metadata without this flag is freed.

### The Unloading Chain (for reference)

```
GC safepoint
  → ClassLoaderDataGraph::do_unloading()          [classLoaderData.cpp:697]
    → MetadataOnStackMark md_on_stack;             [classLoaderData.cpp:704]
      → Threads::metadata_do(mark_on_stack)        [metadataOnStackMark.cpp:48]
      → CodeCache::alive_nmethods_do(mark_on_stack) [metadataOnStackMark.cpp:54]
        → nmethod::metadata_do(mark_on_stack)      [nmethod.cpp:1798]
          → marks all metadata_type relocations
    → for each ClassLoaderData:
      → is_alive()?
        → YES: free_deallocate_list()              [classLoaderData.cpp:710]
          → for each Metadata: if !on_stack() → FREE  [classLoaderData.cpp:437]
        → NO: unload()                             [classLoaderData.cpp:717]
          → classes_do(notify_unload_class)        [classLoaderData.cpp:306]
```

### Why It May Not Manifest Now

The `interface_klass` is normally kept alive by the implementing class's `transitive_interfaces`. If the implementing class is alive (has live instances or is otherwise reachable), the interface klass won't be unloaded. The stub's dangling pointer scenario requires:

1. The implementing class's class loader becomes unreachable
2. The implementing class is unloaded
3. The interface_klass is also unloaded (no other references)
4. The stub's embedded pointer becomes dangling

### Potential Fix (Not Implemented)

**Option A: Add `metadata_do` to CodeBlob hierarchy**

1. Add `virtual void metadata_do(void f(Metadata*))` to `CodeBlob` with default empty implementation.
2. Override in `YuhuRuntimeStub` to report the `interface_klass`.
3. Add `CodeCache::metadata_do(void f(Metadata*))` that iterates all CodeBlobs.
4. Hook into `MetadataOnStackMark` constructor: `CodeCache::metadata_do(Metadata::mark_on_stack)`.

**Option B: Global tracking list in YuhuRuntime**

1. Maintain a static `GrowableArray<Metadata*>*` of all interface klasses used by stubs.
2. Register each `interface_klass` in `generate_interface_call_stub`.
3. Add a static `mark_stub_metadata(void f(Metadata*))` method.
4. Hook into `MetadataOnStackMark` constructor.

Both options ensure `Metadata::mark_on_stack` is called on the embedded `interface_klass`, preventing its deletion during class unloading.

## Lessons Learned

1. **Always check `itable_index()` validity before generating itable dispatch.** A method declared in an interface may not have an itable index if it's non-virtual (static interface method, or resolved to a non-virtual target).
2. **`ciMethod::itable_index()` returns -2 for non-virtual methods.** This is `Method::nonvirtual_vtable_index`, not a bug in the index computation. The caller must check `has_itable_index()` or `itable_index() >= 0`.
3. **RuntimeStubs don't participate in metadata GC tracking.** Any metadata pointer embedded in a RuntimeStub is invisible to `nmethod::metadata_do` and `MetadataOnStackMark`. If the metadata can be unloaded independently, the stub will have a dangling pointer. This is a latent defect that may manifest under class unloading pressure.
