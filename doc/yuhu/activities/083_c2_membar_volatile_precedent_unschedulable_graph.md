# 083: Unsafe Volatile Oop Store — Barrier Precedent Anchored Across a Control Boundary (`!!! Unschedulable graph !!!` in `ConcurrentHashMap::setTabAt`)

**Date:** 2026-10-30
**Status:** Root-caused and fixed. The illegal edge is structurally gone; the deterministic replay of the exact failing compile now runs to completion, as does the real application compile of `setTabAt` at tier 4.
**Severity:** High — a **graph-construction** defect introduced by this fork, not a GC bug and not a backend bug. It aborts C2 (`assert(false) failed: unscheduable graph`) on a shape that appears in real code (`Unsafe.putObjectVolatile` on a possibly-null base object), i.e. every `ConcurrentHashMap` tab store.
**Related commits:** `365d21a943` (introduced the edge, as part of the `MemBarNode::_kind` work),
`8985773d9a` (`fix: 2026-08-21_C2_MemBarAcquire_DecodeN_Precedent_Bug` — same family: a barrier
*precedent* edge created without a dominance check).
**Related docs:** `doc/bugs/2025-11-03_MemBarNode_Kind_Not_Set_Bug.md` (the commit that added the pairing machinery), [082](082_narrow_oop_encode_decode_fold_stale_oop.md) (another case where "it only fails under one configuration" was a red herring).

---

## 1. Problem Summary

`hotspot/src/share/vm/opto/library_call.cpp`, `inline_unsafe_access()`, creates the volatile-store
barrier pair. The fork's `_kind` work made the trailing barrier take the **store node as its
precedent** so that aarch64.ad can elide both `dmb`s and emit a single `stlr`. For the one shape
where the access type is `T_OBJECT` and the base's nullness is **not** provable, the store is built
*inside one arm* of the heap-or-native diamond and the barrier is anchored *on the diamond's merge*.
The arm-local store does not dominate that merge, so the barrier has two inputs whose blocks are
incomparable in the dominator tree, and GCM has no block to put it in.

Two things make this worth writing down:

- **the node is not the problem, its 6th input is.** Upstream builds the identical `MemBarVolatile`
  at the identical anchor; it simply passes no precedent.
- **the crash is GC-correlated but not GC-caused.** The illegal edge is created under every GC.
  G1 changes how the CFG is *partitioned into blocks*, which decides whether the assert that
  detects the violation is ever reached.

## 3. Reading the Dump — the Name Is a Trap

`unnecessary_membar_volatile` / `unnecessary_membar_release` are the **mach node names generated by
adlc from the instruct names** whose *predicate* decides that the `dmb` is unnecessary. The node
exists precisely so the matcher has something to match, and its encode prints
`block_comment("membar_volatile (elided)")`. So the name asserts that *the instruction* is
unnecessary — never that the node is. Reading "unnecessary" as "bogus node" sends the investigation
in the wrong direction, and `-XX:+PrintOptoAssembly` never prints those names at all (it prints the
format text: `stlrw`, `membar_volatile`, `membar_volatile (elided)`), so grepping for them yields
nothing and looks like a negative result.

Note also that the indices in this dump are **mach** indices: `Matcher::match()` calls
`C->set_unique(0)` (`matcher.cpp:343-348`) and renumbers the ideal graph into the mach graph.
Mach `6` ≡ ideal `210`, mach `85` ≡ ideal `108`, mach `7` ≡ ideal `205`.

## 4. Root Cause: the Builder Used a Value from Inside an Arm After Leaving the Arm

The defect is in the fork's hunk (commit 365d21a943). Pre-image, `git show 365d21a943^:src/share/vm/opto/library_call.cpp`:

```cpp
        } __ end_if();
        final_sync(ideal);
#undef __
...
  if (is_volatile) {
    if (!is_store) insert_mem_bar(Op_MemBarAcquire);
    else           insert_mem_bar(Op_MemBarVolatile);        // <- upstream: no precedent, same anchor
  }
```

The commit added, after `final_sync`, a "recover the store from memory state" block:

```cpp
        if (is_volatile && is_store && store == NULL) {
          Node* mem = memory(alias_type->index());
          if (mem->is_Store()) { store = mem; }
        }
```

and then `insert_mem_bar_trailing_store(Op_MemBarVolatile, store)`. By the time that block runs,
`final_sync(ideal)` has moved `control()` to the diamond **merge**, while `store` names the store
that was created **inside the heap arm**. The recovery block therefore reaches across a control
boundary. In the failing graph (post-GVN, pre-fix, `-XX:+PrintIdeal`):

| node | what it is | `in(0)` (control) | mach block | dom depth |
|---|---|---|---|---|
| 210 | `MemBarVolatile` at the join | 205 `Region === 205 47 197` | B10 | 3 |
| 108 | `StoreN === 104 39 31 107`, heap arm | 104 `Region === 104 101 65` (G1 SATB **pre**-barrier merge) | B7 | 4 |
| 203 | `StoreN === 47 …`, native arm | 47 `IfFalse` | — | — |

`find_deepest_input` (`gcm.cpp:182-202`) iterates `n->len()` — so a *precedent* edge counts as an
input just like control and memory do — and asks for the one input block that dominates all others.
The join (depth 3) and the arm (depth 4) are incomparable: the other arm reaches the join through
`45 If → 47 IfFalse → 205` without ever passing 104. GCM is allowed to look only for a *linearly
ordered* set of input blocks, so the graph has no legal schedule. The memory input is irrelevant to
the conflict: it is the `MergeMem` **of** the join, and it is properly ordered.

The detection site is not the defect site. `verify_graph_edges` checks use/def integrity only, and
GVN and the matcher both preserve the edge; GCM is the first pass that asks a *dominance* question.
That is what makes this class of bug look like "the compiler broke during scheduling".

## 5. Why It Blew Up Only Under G1 (the generalizable part)

Mach blocks are headed by **control targets** — `Region`, `If`, `Call`, `Return` — and straight-line
nodes are absorbed into the block of their enclosing control target. So what matters is not whether
the store dominates the join (it never does, under any GC) but whether the store *lands in a
different block with a strictly greater `dom_depth`*:

| GC | store's `in(0)` | store's block | join's block | `gcm.cpp:191` strict `<` | `assert_dom` |
|---|---|---|---|---|---|
| Serial / Parallel | `IfTrue` — the arm head, i.e. the block header itself | absorbed into the arm-head block | the block headed by the join `Region` | equal depth → never taken | **never called** |
| G1 | `Region` — the SATB pre-barrier merge, inserted *above* the arm head | its own block, one dom level deeper | shallower | fires | **called → abort** |

The same reasoning is visible verbatim in the code: `assert_dom` is a `DEBUG_ONLY` call placed
*inside* the `if (deepb_dom_depth < inb->_dom_depth)` branch (`gcm.cpp:191-195`), so an unordered
pair of inputs at the *same* depth is simply not detected — the node gets placed in that depth and
compiles. Under Serial the illegal edge is present and harmless-looking; under G1 it is fatal.

*Provenance of the Serial/Parallel row:* it was read off the pre-fix replay logs
(`-XX:+ReplayCompiles` + `-XX:+PrintIdeal`, `m8.sh`), which showed the identical arm-local precedent
under Serial (`68 MemBarVolatile === 64 1 67 1 1 52` with `52 StoreN === 46  …` and the join
`64 Region === 64 47 46`, both arms direct, no barrier Regions). Those files have since been
regenerated post-fix and now show `req()==5`; re-derive the row by checking out `365d21a943`'s tree,
rebuilding, and running `bash /tmp/g1fix/m8.sh`. The mechanism itself does not depend on that log:
the diamond, the join and the precedent are all created before any GC-specific barrier is inserted.

Consequence, and this is the sentence to remember: **a compiler failure that appears only with one
GC is not evidence about that GC.** GC barrier insertion changes block granularity, i.e. which
pre-existing graph violations the checker can reach. G1 did not break `setTabAt`; it turned on the
light in a room where the floor was already cracked. (Retracted on the way here: an earlier
phrasing of mine, "G1 tips a latent violation into failing", was underspecified — G1 does not tip
anything, it only changes whether the violation is *observable*.)

Two secondary facts, both measured, that kept the hunt honest:

- The other `MemBarVolatile` in the same dump (`150 MemBarVolatile === 145 1 149 1 1 108`, present
  byte-identical before and after this fix) is legal: it is the upstream **G1 post-barrier** card-mark
  StoreLoad membar (`graphKit.cpp:4256-4257`, `insert_mem_bar(Op_MemBarVolatile, oop_store)`), and it
  is anchored *inside* the barrier's own arm, below its precedent. Only G1 has it, and it is not the
  failing node. Do not confuse it with the unsafe-access barrier.
- `G1SATBCT` is not a flag in this tree, so the obvious A/B (turn SATB barriers off and see) cannot
  be run. The block-granularity argument above replaces it.

## 6. Muting the Assert Is Not a Fix (measured)

| attempt | outcome |
|---|---|
| `-XX:SuppressErrorAt=/gcm.cpp:177` | second abort at `gcm.cpp:282` — `assert(get_block_for_node(parent) == get_block_for_node(parent->in(0))) "Pinned Node should be at the same block as its control edge"`, i.e. the *next* checker finds the same inconsistency |
| both suppressed | `rc=0`, but **no assembly is emitted for `setTabAt` at all** — the compile is lost, the program runs on interpreted/C2-other code |

Worth recording because "the assert is over-strict, G1 just hits it" is exactly the hypothesis that
the suppression experiment falsifies: the graph really is unschedulable, so the fix has to be in the
graph.

Also note what the assert does *not* tell you: in a product build the whole check is compiled out
(`#ifdef ASSERT`), and the node is then simply placed in a block below its own control input. What
that produces mechanically — a barrier missing on one arm, or a later failure elsewhere — was **not
measured**. Absence of a product-build crash is not evidence of correctness here.

## 7. The Fix

### 7.1 The constraint that shaped it: barrier pairs are atomic

The obvious one-line fix — "just drop the precedent" — is wrong, and the reason is in the backend.
`unnecessary_release()` (`aarch64.ad:1262-1308`) walks `leading → trailing_membar() → in(Precedent)`
**outside `#ifdef ASSERT`**, and `MemBarNode::trailing_membar()` walked its own loop-exit condition
without a NULL test. So a graph with a `LeadingStore` barrier and no `TrailingStore` partner does not
merely assert — it NULL-derefs at matcher time, **including in product builds**. Demoting only the
trailing half would have traded a debug abort for a shipped crash.

Therefore: **both halves of the pair are decided together, from one boolean, at the site that holds
the knowledge.**

### 7.2 `library_call.cpp` — decide the shape where the shape is created

```cpp
  Node* p = NULL;
  Node* store = NULL;
  // Leading release barrier of a volatile store.  It is upgraded to a
  // LeadingStore barrier (the head of a barrier pair) further down only if the
  // access was not lowered into the heap/native diamond, because in that shape
  // the trailing barrier is anchored on the diamond merge and the arm-local
  // store does not dominate it, which leaves the pair with no legal schedule
  // (PhaseCFG::find_deepest_input rejects unordered input blocks).
  Node* leading_bar = NULL;
  // Set when the volatile store is created inside the heap arm of that diamond.
  bool store_in_diamond = false;
  if (is_volatile) {
    need_mem_bar = true;
    if (is_store)
      leading_bar = insert_mem_bar(Op_MemBarRelease);       // was insert_mem_bar_leading_store(...)
  }
```

the diamond records its own shape at the point it is opened, and the post-`final_sync` recovery block
is deleted outright:

```cpp
        // The store created below lives in one arm of this diamond while the
        // trailing barrier will be anchored on its merge, so it cannot serve as
        // the barrier's precedent.
        store_in_diamond = true;
        IdealKit ideal(this);
...
        } __ end_if();
        final_sync(ideal);
        // control() is now the merge of the diamond.  The heap-arm store is not
        // an input of it (the native arm reaches the merge without it), so this
        // access keeps standalone barriers; the native-arm store is deliberately
        // not captured either, since it is on the other arm.
#undef __
```

and the trailing site makes the single decision:

```cpp
      bool pair_barriers = !store_in_diamond
                           && leading_bar != NULL
                           && store != NULL && store->is_Store();
      if (pair_barriers) {
        MemBarNode* lb = leading_bar->as_MemBar();
        lb->set_leading_store();
#ifdef ASSERT
        lb->set_pair_idx(lb->_idx);
#endif
        insert_mem_bar_trailing_store(Op_MemBarVolatile, store);
      } else {
        assert(store == NULL || store->is_Store() || store->is_top(),
               "volatile store should be a Store or top");
        insert_mem_bar(Op_MemBarVolatile);
      }
```

This is a deviation from the plan I presented before coding, in a better direction: rather than
hoisting a duplicated nullability/type test above the leading barrier, the leading barrier is created
plain and its **kind is upgraded** at the trailing site, so both halves are decided at once, next to
each other, where the dominance knowledge lives. Ordering does not depend on the precedent anyway —
the barrier's memory input is the join's `MergeMem`, which already contains the store's memory state.

### 7.3 `graphKit.cpp` — `_pair_idx` must live on the node that survives GVN

`insert_mem_bar_leading_store` / `_leading_load_store` set the pair index on `mb`, then
`_gvn.transform(mb)` may return an **existing** barrier, and `MemBarNode::trailing_membar()` compares
the index against *that* node. Now:

```cpp
  Node* membar = _gvn.transform(mb);
#ifdef ASSERT
  // Set _pair_idx on the node we keep: GVN may have returned an existing
  // barrier instead of mb, and the trailing half is compared against this
  // index by MemBarNode::trailing_membar().
  membar->as_MemBar()->set_pair_idx(membar->_idx);
#endif
```

with the trailing helpers capturing `uint pair_idx = mb->pair_idx();` *before* the transform and
re-applying it after (`graphKit.cpp:3220-3321`).

### 7.4 `aarch64.ad` and `memnode.cpp` — half a pair must degrade, not deref

- `unnecessary_release()`: missing trailing half → `return false`; precedent read as
  `(trailing_mb->req() > MemBarNode::Precedent) ? trailing_mb->in(MemBarNode::Precedent) : NULL`,
  then `if (mem == NULL) return false;` (`aarch64.ad:1278-1292`).
- `unnecessary_volatile()`: the precedent is read **only** for a trailing-store barrier and
  `req()`-guarded, because `MemBarNode::MemBarNode` sizes itself as
  `TypeFunc::Parms(5) + (precedent ? 1 : 0)` and `Node::in(i)` asserts `i < req()` — an
  unconditional `in(MemBarNode::Precedent)` on a plain `MemBarVolatile` would assert on *every*
  volatile store in the VM. `leading_membar() == NULL` → `return false` (`:1331-1345`).
- `MemBarNode::trailing_membar()`: `} while (trailing != NULL && ...)` plus an explicit
  "no pair → return NULL" exit (`memnode.cpp:3068-3078`).
- `StoreNode::trailing_membar()`: the three pairing asserts moved behind
  `assert(leading != NULL, "trailing membar without a leading half")` (`:2630-2637`).

The fallback for all of these is the same and deliberate: **emit the real `dmb`**. Elision is an
optimization; when the pairing is not provably complete, correctness is cheap and silence is not.

## 8. Options Considered and Rejected

| option | why not |
|---|---|
| mute `gcm.cpp:177` (and `:282`) | falsified by measurement — §6; the graph is genuinely unschedulable |
| drop only the trailing precedent, keep `LeadingStore` kind | turns a debug assert into a matcher-time NULL deref in product builds (§7.1) |

## 10. Cost

Volatile unsafe **oop** stores whose base is ambiguous at compile time — which includes
`ConcurrentHashMap.setTabAt`/`tabAt`, i.e. all of CHM — now emit `str` + two real `dmb`s instead of
`stlr` + elided membars, **under every GC**. Relative to JDK8 upstream the delta is zero: upstream
never passes the precedent, so upstream never elides here either.

Relative to this fork's *pre-fix* build there is a real cost, and it should not be papered over.
Reading the backend path (`aarch64.ad:1357-1368`, `needs_releasing_store` → `StoreNode::trailing_membar()`),
the pre-fix build reached `stlr` + both elisions under Serial and Parallel too — the pairing was
accepted because the kind said so, and nothing in the elision predicates asks a dominance question.
That reading is code-derived, not measured (no pre-fix Serial assembly was captured). If it is right,
the consequence is the uncomfortable one: **the elided form was being emitted out of a graph the VM
classifies as unschedulable**, and the fix removes it everywhere rather than only where the assert
fires. That is the correct trade — a schedule that exists by luck of block partitioning is not a
schedule — but it is a trade, not a free win, and §11 item 1 is what pays it back.

## 11. Open Items

## 12. Why This Is a Typical Issue — the Rules to Carry Forward

1. **Any new *edge* between a value and a node anchored somewhere else is a dominance claim, not a
   data-flow claim.** Barrier precedents, pointer/declaration pairs, projection back-edges: if the
   producer was created under a control that the consumer is not, the graph has no schedule. Grep
   for `insert_mem_bar`-style helpers that take a node captured before a control move and ask, for
   each, "is this still dominated here?"
2. **GCM is the first dominance checker in the pipeline, so its assert location is a red herring.**
   `verify_graph_edges`, GVN and the matcher all preserve an illegal edge; the abort lands in
   `Code_Gen`, hundreds of passes after the defect.
3. **"It only fails with GC X" is a statement about block granularity, not about GC X.** Mach blocks
   are headed by control targets, so any barrier that inserts a `Region` between an arm head and its
   store moves the store one dom level deeper and can switch a latent violation from invisible to
   fatal. Before blaming a GC, check whether the violating edge exists under the other GCs too.
4. **Node names in the *mach* graph describe the emitted instruction, not the node's necessity**
   (`unnecessary_membar_volatile` = "the `dmb` is elided"), and `PrintOptoAssembly` prints instruction
   format text rather than instruct names. Verify a claim about assembly by grepping for the format
   text (`stlrw`, `membar_volatile (elided)`) and by checking the grep cannot match zero for a
   structural reason — a false negative here costs hours.
5. **Optimization machinery that spans two nodes must be decidable atomically.** If the backend
   follows a link from one node to its partner (here `leading → trailing → precedent`), then a
   graph that keeps only one side of the link is not a missed optimization but a NULL deref — and
   `#ifdef ASSERT`-only guards around those derefs are exactly the product-build bug.
6. **Prefer "degrade to the unoptimized but correct form" over "assert"** whenever the missing
   information is a legality question the builder is entitled not to have answered.
7. **Reproduce compiler bugs deterministically** — `-XX:+ReplayCompiles -XX:ReplayDataFile=…` with
   `-XX:CompileCommand=compileonly,<class>::<method>` gives a single-compile, GC-independent loop
   that turns each hypothesis into a two-minute experiment. The `assert_dom` dump plus `PrintIdeal`
   was sufficient for the whole diagnosis; no debugging of the optimizer was needed.
8. **When a suppression experiment makes the error go away and the output is still wrong, the assert
   was right.** §6 is the discipline: try the suppression, look for the *missing nmethod*, retract
   the "over-strict assert" hypothesis.
